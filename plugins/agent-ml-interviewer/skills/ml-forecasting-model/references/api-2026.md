## 1. Стаціонарність

```python
from statsmodels.tsa.stattools import adfuller, kpss
adf_stat, adf_p, *_ = adfuller(y, autolag="AIC")     # H0: одиничний корінь
kpss_stat, kpss_p, *_ = kpss(y, regression="c", nlags="auto")  # H0: стаціонарний
```

- **`kpss` видає `InterpolationWarning`**, коли p за межами таблиці
  (`"p-value is greater than the indicated value"`): це не помилка, p насичена
  на 0.10 (згори) або 0.01 (знизу). Ловити: `warnings.catch_warnings()`.
- `regression="c"` — стаціонарність навколо константи; `"ct"` — навколо тренду
  (для перевірки trend-stationary).
- ADF `autolag="AIC"` сам обирає число лагів; фіксувати `maxlag` лише навмисне.

## 2. Класичні моделі

```python
from statsmodels.tsa.arima.model import ARIMA
from statsmodels.tsa.statespace.sarimax import SARIMAX
from statsmodels.tsa.holtwinters import ExponentialSmoothing

# ARIMA(p,d,q)
res = ARIMA(y_train, order=(2, 1, 2)).fit()
fc  = res.forecast(steps=H)                      # точковий прогноз
ci  = res.get_forecast(H).conf_int()             # інтервал прогнозу

# SARIMAX із сезоном і екзогенними X
res = SARIMAX(y_train, exog=X_train,
              order=(1,1,1), seasonal_order=(1,1,1,12)).fit(disp=False)
fc  = res.forecast(H, exog=X_future)             # X_future ОБОВ'ЯЗКОВИЙ

# ETS / Holt-Winters
res = ExponentialSmoothing(y_train, trend="add",
        seasonal="add", seasonal_periods=12).fit()
fc  = res.forecast(H)
```

- **`SARIMAX.forecast(exog=...)` вимагає майбутні `X`** — якщо їх нема в проді,
  екзогенні предиктори непридатні (їх самих треба прогнозувати).
- `ExponentialSmoothing`: `trend`/`seasonal` ∈ `{"add","mul",None}`;
  `"mul"` тільки для строго додатних рядів (інакше `ValueError`).
- `.fit(disp=False)` глушить лог оптимізатора SARIMAX.
- Довгі ряди + високий порядок → `ConvergenceWarning`; це сигнал спростити
  порядок, не ігнорувати.

## 3. Global ML: лаги + gradient boosting

`pmdarima`, `prophet`, `sktime`, `darts`, `neuralprophet` — **у середовищі
відсутні** (перевірено імпортом). Global-forecasting будується руками на
`lightgbm` (є, 4.6.0) або `sklearn`:

```python
import numpy as np
from lightgbm import LGBMRegressor

def make_lags(series, L=12):
    X = np.column_stack([series[i:len(series)-L+i] for i in range(L)])
    return X, series[L:]

# global: складаємо лаг-ознаки з БАГАТЬОХ рядів у одну навчальну матрицю
Xs, ys = [], []
for s in all_series:
    X, y = make_lags(s)
    Xs.append(X); ys.append(y)
model = LGBMRegressor(n_estimators=100, verbose=-1).fit(np.vstack(Xs),
                                                        np.concatenate(ys))

# рекурсивний прогноз на H кроків для одного ряду
hist = list(one_series)
for _ in range(H):
    x = np.array(hist[-12:]).reshape(1, -1)
    hist.append(model.predict(x)[0])
preds = hist[-H:]
```

- `LGBMRegressor(verbose=-1)` — глушить епохний лог.
- **Ідентичність ряду подавати ознакою** (статичні атрибути, one-hot/ID),
  інакше global-модель зливає всі ряди в один.
- Лаг-ознаки будуються ТІЛЬКИ з минулого — інакше витік (`ml-validation-design`).

**Втрати для переміжного/скошеного попиту (перевірено живим викликом, 4.6.0):**

```python
LGBMRegressor(objective="tweedie", tweedie_variance_power=1.5)  # 1<p<2
LGBMRegressor(objective="poisson")                              # лічильні
LGBMRegressor(objective="quantile", alpha=0.9)                  # квантиль (інтервали)
```

- `tweedie_variance_power` у (1, 2); дефолт 1.5. `p→1` ближче до Poisson,
  `p→2` до Gamma. Прогноз клемпити `np.clip(pred, 0, None)` — від'ємних продажів
  не буває.
- `objective="tweedie"/"poisson"/"quantile"` **усі доступні** в 4.6.0 (на відміну
  від деяких sklearn-об'єктів). `sklearn.linear_model.TweedieRegressor(power=,
  link="log")` теж є — для лінійної альтернативи.
- Для інтервалів прогнозу без statsmodels — три `quantile`-моделі (0.1/0.5/0.9).
- Тюнінг самого бустингу — `ml-tree-ensemble-params` (n_estimators↔learning_rate).

## 4. Метрики

```python
from sklearn.metrics import mean_absolute_error, mean_squared_error
# MASE вручну — у sklearn немає
def mase(y_true, y_pred, y_train, season=1):
    naive = np.mean(np.abs(y_train[season:] - y_train[:-season]))
    return mean_absolute_error(y_true, y_pred) / naive
```

- **`mean_absolute_percentage_error` є в sklearn, але вибухає на нулях**
  (перевірено: 1.1·10¹⁵ з одним нулем у `y_true`). При нулях/від'ємних — MASE.
- **`mean_squared_error(..., squared=False)` у 1.9 кидає `TypeError`** —
  параметр `squared` **видалено** (не deprecated з ворнінгом, а прибрано;
  перевірено живцем). RMSE тепер лише через `root_mean_squared_error` (є в 1.9).
  Той самий клас зламу, що й `AdaBoost(algorithm=...)`.
- MASE в sklearn немає — рахувати вручну (код вище); `season` = період для
  сезонного наївного знаменника.

## 5. Валідація (делеговано, але тут — сплітер)

## 6. Zero-shot foundation models: TimesFM 2.5 і Chronos-2 — перевірено 2026-08-01/08

**Версія пакета ≠ версія моделі.** Модель «TimesFM 2.5» живе в PyPI-пакеті
`timesfm` **2.0.x** (2.0.0 — 2026-06-05, чинна 2.0.2 — 2026-07-02;
`requires_python >=3.10`). `pip install timesfm==2.5` не існує. Extras (з
метаданих wheel): `[torch]`, `[flax]`, `[xreg]`; ліцензія Apache-2.0.
**`[xreg]` (коваріати) тягне `jax[cuda]` — на Windows нативно недоступний**,
тобто екзогенні X у цій версії — фактично лише Linux/CUDA.

```python
# pip install "timesfm[torch]"   (тягне torch >=2.0; тут поставило 2.13.0)
import numpy as np, timesfm
model = timesfm.TimesFM_2p5_200M_torch.from_pretrained(
    "google/timesfm-2.5-200m-pytorch")        # чекпоінт 882 MB у ~/.cache/huggingface
model.compile(timesfm.ForecastConfig(
    max_context=144, max_horizon=24,
    normalize_inputs=True,
    use_continuous_quantile_head=True,        # інакше квантилі не мають сенсу
    fix_quantile_crossing=True))
point, quant = model.forecast(horizon=24, inputs=[series_a, series_b])
# point: (n_series, H); quant: (n_series, H, 10)
```

- **Публічний API пакета 2.0.x — рівно два імені**: `TimesFM_2p5_200M_torch`
  і `ForecastConfig`. Класи 1.x (`TimesFm`, `TimesFmHparams`, параметр `freq`)
  **повністю видалені** — код за старими туторіалами не імпортується.
- **`forecast(horizon, inputs)` не має параметра частоти** — 2.5 сам дає раду
  з будь-яким кроком ряду (у 1.x `freq` 0/1/2 був обов'язковою підказкою).
- `forecast()` без `compile()` → `RuntimeError: Model is not compiled` (чітко).
  А от **`horizon` понад `max_horizon` і контекст понад `max_context`
  працюють МОВЧКИ** (перевірено: compile з max_horizon=24, запит 48 → (1, 48)
  без ворнінга; контекст 288 при max_context=144 → тихо всічено). Той самий
  клас тихої відмови, що незважений scorer.
- **Квантильна голова:** `quant[..., 1:10]` = децилі q10..q90 (монотонні при
  `fix_quantile_crossing=True`); `quant[..., 0]` — НЕ точковий прогноз
  (перевірено: не збігається з `point`). Покриття міряти на backtest: 80%-смуга
  дала 87.5% на гладкому ряді й **37.5% на переміжному** (див. derivations §7).
- `infer_is_positive=True` (дефолт) — на ряді з нулями мінімальний прогноз
  0.0293, від'ємних немає; клемп не потрібен.
- Вартість: завантаження+ініціалізація 127 с (перший раз, з мережею), далі
  інференс **1.12 с на CPU** для 2 рядів × H=24. GIFT-Eval-лідерство — заявка
  Google, тут не перевірялась.
- **Ставити в окремий venv**: у venv з `numpy 2.5.1` (який тягне свіжий torch)
  **statsmodels 0.14.6 не імпортується** (`DLL load failed` у
  `tsa.statespace._initialization` на Windows) — в основному середовищі з
  numpy 2.2.6 той самий statsmodels працює. Класика + foundation model в
  одному середовищі — конфліктна зона ABI.

### Chronos-2 (`chronos-forecasting` 2.3.1) — перевірено 2026-08-08

```python
# pip install chronos-forecasting     (torch уже потрібен)
from chronos import Chronos2Pipeline
pipe = Chronos2Pipeline.from_pretrained("amazon/chronos-2")   # 455.8 MB, 119.5M параметрів
quant, mean = pipe.predict_quantiles(inputs=[serA, serB], prediction_length=24)
# quant: (n_series, n_variates, H, 9 децилів); mean: (n_series, n_variates, H)
task = {"target": train,
        "past_covariates":   {"temp": temp[:n]},
        "future_covariates": {"temp": temp[n:n+H]}}            # known-future X
quant, mean = pipe.predict_quantiles(inputs=[task], prediction_length=H)
```

- **Протилежна до timesfm стратегія API:** пакет ЗБЕРІГ усі покоління
  (`ChronosPipeline`, `ChronosBoltPipeline`, `Chronos2Pipeline` співіснують),
  але **перейменував перший аргумент** `predict_quantiles`: `context=` (ген-1)
  → `inputs=` (ген-2). Код під Chronos-1 падає з
  `TypeError: missing ... 'inputs'` на методі з тією самою назвою.
- **Вихід має вісь варіат** — `(n_series, n_variates, H, Q)`, навіть для
  univariate (n_variates=1): індексувати `q[i, 0]`, інакше тихий broadcast-збій.
- Коваріати — dict-вхід (`target` / `past_covariates` / `future_covariates`),
  працює на CPU/Windows (на відміну від timesfm `[xreg]`→`jax[cuda]`);
  є `cross_learning=True` для переносу між рядами. Виміряно: коваріати, чия
  інформація ВЖЕ є в історії цілі (детермінований сезон), дають нуль
  (MAE 0.349 → 0.355). Третя точка входу — **`predict_df()`** для довгого
  DataFrame (`id_column`/`timestamp_column`/`target`, `future_df=` для
  known-future X) — повертає довгий df з колонками `predictions` і квантилями.
- **Файнтюн LoRA — `pipe.fit(tasks, finetune_mode="lora", lora_config=...,
  validation_inputs=..., num_steps=..., callbacks=[EarlyStoppingCallback])`**
  (потрібен `peft`; перевірено живцем: 50 кроків на CPU — 5.2 хв, повертає
  новий `Chronos2Pipeline`). Два факти, впіймані власними падіннями:
  (а) **ряди у `validation_inputs` мають довжину ≥ min_past +
  prediction_length** — передавати ПОВНИЙ префікс історії, а не лише
  валідаційне вікно (інакше `ValueError: dataset is empty after filtering`);
  (б) `fit(**kwargs)` прозоро пробрасывает решту в `TrainingArguments`, тож
  набір аргументів прив'язаний до версії transformers: **`overwrite_output_dir`
  видалено у transformers 5.x** (тут 5.14.1) — авторські ноутбуки під 4.x
  падають TypeError'ом на свіжому стеку. Числа
  ноутбуків автора TDS (GPU, будівлі, строгий хронологічний спліт): коваріати
  вже zero-shot ріжуть WAPE удвічі (8.4→4.2%); файнтюн ЛИШЕ по цілі дає
  скромні −7..9%, файнтюн з коваріатами — −27..33% (до 2.8%); **coverage
  після файнтюну звужується** (98→91%); **cold-start (3 дні контексту)
  адаптер НЕ рятує: 15.6→15.5%** — це notebook-only діагностика, якої немає
  в тексті статті. Правило: спершу zero-shot + коваріати, файнтюн — лише коли
  виміряний розрив виправдовує вартість супроводу адаптера.
- **Прогноз як детектор аномалій** (ноутбук 3): скор = відстань поза
  квантильною смугою / півширина смуги; коваріати вбивають хибні тривоги
  (precision 67.6% → **96.3%**, recall 68.7→77.6% на 4 інжектованих подіях) —
  «висока витрата в спекотний робочий день — норма, та сама вночі — ні».
  Поступовий дрейф ловиться частково (33/48 год) — стартує під смугою.
- `config.model_type == "t5"` — це **тег сім'ї** в HF-конфізі; популярний
  листікл на цій підставі приписує Chronos-2 «мовне моделювання з варіантами
  9M-710M» — насправді це опис **Chronos-1/Bolt**; `amazon/chronos-2` —
  один реліз 119.5M з патч-входом і прямою квантильною головою (пораховано
  `sum(p.numel())`, не з README).
- Інференс повільніший за timesfm: **5.1 с** проти 1.1 с CPU (2 ряди, H=24);
  завантаження з кеша 2.5-5.5 с. `infer_is_positive`-аналога немає: на
  переміжному ряді q10 йде трохи нижче нуля (−0.006) — клемп за потреби.

**Ландшафт без перевірки** (названі-не-верифіковані, 2026-08): MOIRAI-2

## 7. Автоматична екстракція ознак: tsfel / feature-engine — перевірено 2026-08-01

**tsfel 0.2.0** — домени `statistical` (31 ознака), `temporal` (14),
`spectral` (111), `fractal` (6); повний конфіг = 156 ознак на вікно.

```python
import tsfel
cfg = tsfel.get_features_by_domain("temporal")          # або statistical/fractal
X = tsfel.time_series_features_extractor(cfg, df, fs=1, verbose=0)
```

- **Пастка: домен `spectral` при `fs<=2` падає** з
  `ValueError: cannot reindex on an axis with duplicate labels` (перевірено:
  fs=1 і fs=2 падають, fs>=10 працює) — тобто дефолтний
  `get_features_by_domain()` (усі домени) **ламається рівно на чесному fs=1
  для денних/місячних бізнес-рядів**. Обхід: тягнути домени без spectral.
  Підвищення fs заради обходу міняє значення частотних ознак — це не фікс.
- Екстрактор рахує ознаки **на все подане вікно** — подавати train-вікна
  rolling-origin, а не весь ряд (інакше витік майбутнього в ознаки).

**feature-engine 1.9.4** — sklearn-сумісні трансформери лагів/вікон:

```python
from feature_engine.timeseries.forecasting import LagFeatures, WindowFeatures
LagFeatures(variables=["y"], periods=[1, 2])            # y_lag_1, y_lag_2
WindowFeatures(variables=["y"], window=[3], functions=["mean", "std"])
```

- **Вікна зсунуті за замовчуванням** (перевірено: window_3_mean у рядку t
  рахується з t−3..t−1, БЕЗ y[t]) — безпечно за конструкцією, на відміну від
  сирого `df.rolling(3).mean()`, який включає поточний рядок.
- Обидва — трансформери з `fit/transform`, лягають у `Pipeline` всередині CV.

**Сирі pandas-вікна — виміряний напрям витоку (2026-08-08).** Популярний
туторіал «10 one-liners» позначає `rolling().mean()` безпечним, а
`ewm().mean()` — «потребує майбутніх точок». Виміряно рівно навпаки:

- `rolling(3).mean()` у рядку t **включає y[t]** (на `[1,2,3,4,100]` останнє
  значення 35.67, не 3.0) — як ознака для прогнозу y[t] це витік ЦІЛІ.
- `ewm(span=5).mean()` **строго каузальний**: зміна всіх майбутніх значень не
  змінює значення в t (перевірено тотожністю) — витоку з майбутнього немає,
  але поточний рядок він теж включає.
- Універсальний фікс обом — **`.shift(1)`** (те, що feature-engine робить за
  замовчуванням). Готова обгортка «модель → форкастер» без ручних лагів —
  `sktime.forecasting.compose.make_reduction(regressor, strategy="recursive")`
  (названо-не-верифіковано, sktime у середовищі відсутній).

В основному середовищі пака `sktime`/`tsfresh`/`featuretools`/`tsfel` —
**відсутні** (без змін із §3); tsfel/feature-engine перевірялись в окремому
venv. На PyPI: sktime 1.1.0, feature-engine 1.9.4, tsfel 0.2.0 (2026-08-01).

## 8. Prophet 1.3.0 — перевірено 2026-08-08 (окремий venv)

`pip install prophet` на Windows/Python 3.12 ставиться чисто (1.3.0, wheels з
компільованим Stan) — книжкова рекомендація «лише через Anaconda» застаріла.
В основному середовищі пака prophet, як і раніше, **відсутній**.

```python
from prophet import Prophet
m = Prophet()                     # дефолти перевірено полями об'єкта:
# n_changepoints=25, changepoint_range=0.8, changepoint_prior_scale=0.05,
# interval_width=0.8, mcmc_samples=0, growth='linear' ('logistic'/'flat' теж є)
m.fit(df)                          # df: колонки ds (дата) і y
future = m.make_future_dataframe(periods=24, freq="MS")   # freq ОБОВ'ЯЗКОВО не-денним
fc = m.predict(future)             # yhat, yhat_lower, yhat_upper
```

- **`interval_width=0.8`** — «інтервал Prophet» за замовчуванням 80%, не 95%.
- **`mcmc_samples=0`** (MAP): невизначеність = тренд + шум, БЕЗ сезонної
  складової; на сезонному ряді A покриття 80%-смуги — **62.5%** (проти
  87.5%/79.2% у TimesFM/Chronos-2, derivations §7). Повна байєсова —
  `mcmc_samples>0`, на порядки повільніше; `regressor_coefficients()` без MCMC
  дає `coef_lower == coef == coef_upper` (виродження меж — не баг, а MAP).
- **Змінні точки лише в перших 80% історії** (`changepoint_range=0.8`, 25
  точок): злам тренду в останніх 20% буде вигнутий трендом, а не пійманий
  точкою зламу.
- Пропуски **дозволені** (без інтерполяції) — тому викид «лікують»

  (`lower_window`/`upper_window`), не NaN.
- Автосезонності на місячних даних: лишається тільки `yearly` (перевірено
  `m.seasonalities`); weekly/daily самовимикаються.

  cross_validation, performance_metrics`;
  `cross_validation(m, initial="730 days", period="30 days", horizon="90 days")`.
